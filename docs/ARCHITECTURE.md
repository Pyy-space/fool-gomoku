# GomokuAI 架构设计

> ⚠️ **本文档描述的是「完整版」的架构**（含识别下棋的 vision/ control/ window 层）。
> 本仓库 `fool-gomoku` 是 **web 版**，只保留纯引擎部分（人机对弈 + 在线学习 + 实验室调参），
> 识别下棋相关代码已移除，完整版在本地 `GomokuAI/` 目录。web 版的实际结构见 [../README.md](../README.md) 的目录树。

> 通用五子棋视觉对弈框架：既能本地人机对弈，也能通过屏幕识别在任意窗口/网页程序中落子。

---

## 1. 设计目标

| 编号 | 目标 | 落点 |
|---|---|---|
| G1 | **通用**：不绑定《燕云十六声》，任何五子棋程序的窗口/网页都能接 | `vision` 层 + Profile 机制 |
| G2 | **双模式**：本地手动布子 / 自动读屏落子 | `adapters` 抽象层 |
| G3 | **可移植**：整个文件夹可整体搬走 | 全部相对路径，`Path(__file__)` 基准 |
| G4 | **强棋力**：目标是赢 | 战术层 + VCF + αβ 搜索 + 棋型评估 |
| G5 | **标准规则**：15×15，黑棋禁手 | `engine/rules.py` 可切换 casual / renju |
| G6 | **执色未知** | 运行期自动判定，不写死 |

## 2. 为什么做 Web 版（而不是本地小窗程序）

结论：**改成"本地 Web 服务 + 浏览器 UI"**，理由按重要性排序：

1. **零安装负担**。本机已装 Flask 3.1 + Flask-SocketIO 5.5，`python run.py` 就能起，不用装 Qt / Tk 的额外依赖。
2. **调试友好**。识别管线最容易出错，Web 端可以把「原图 / 网格线 / 交点 / 分类结果」四张图层叠在一起实时看，这是本地 Tk 窗口很难做到的。
3. **和浏览器版对手天然对齐**。对手若是网页版五子棋，我们也是浏览器，可以直接用 CDP/Playwright 读 DOM，比截图识别稳得多；用同一套 Web UI 管两边，最自然。
4. **可扩展成远程**。以后想在另一台机器看棋局，改个监听地址就行。

> 本地小程序的唯一优势是"点一下就开"，用 `start.bat` 一行解决，不构成理由。

## 3. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  app/  Web UI (Flask + SocketIO)                        │
│  棋盘渲染 / 手动落子 / 识别预览 / 引擎分析 / 对局控制    │
└───────────────┬─────────────────────────────────────────┘
                │ Session（对局状态机，单一事实来源）
┌───────────────▼─────────────────────────────────────────┐
│  adapters/  对局适配层（抽象）                            │
│   LocalAdapter  —— 本地棋盘，纯引擎推演                   │
│   WindowAdapter —— 任意窗口程序（截图 + 点击）            │
│   WebAdapter    —— 浏览器网页（DOM / CDP 优先）           │
└───────────────┬─────────────────────────────────────────┘
                │ 每帧 BoardState
┌───────────────▼─────────────────────────────────────────┐
│  vision/  视觉识别层                                     │
│   window   窗口枚举 / 客户区 / DPI / 前后台               │
│   capture  截图后端（mss / PrintWindow / BitBlt）        │
│   grid     网格检测与标定（一次标定，长期复用）           │
│   stones   交点取色 → 黑/白/空 分类                       │
│   detector 组合成 15×15 矩阵 + 置信度                     │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  engine/  棋理引擎（纯 Python，零 UI 依赖，可单测）       │
│   board    棋盘 / 落子 / 悔棋 / 胜负 / 禁手               │
│   patterns 棋型识别（活四/冲四/活三/眠三...）             │
│   tactics  必杀 / 必防 / VCF（连续冲四取胜）              │
│   eval     局面评估                                      │
│   search   迭代加深 αβ + 置换表 + 走法排序                │
│   mcts     蒙特卡洛树（沿用原项目思路，作为备选引擎）      │
│   opening  开局库                                          │
└─────────────────────────────────────────────────────────┘
```

**关键约束**：`engine` 不 import 任何视觉或 UI 代码，保证它可以脱离屏幕单独测试和跑 bench。

## 4. 通用性怎么实现（G1 的核心）

不写死任何界面坐标。每个目标程序对应一个 **Profile（JSON）**：

```json
{
  "name": "yanyun",
  "window": { "title_regex": "燕云|Where Winds Meet", "class_regex": "" },
  "board": {
    "size": 15,
    "origin": [612, 338],
    "spacing": 43.5,
    "axis": "xy"
  },
  "theme": {
    "board_bg": [222, 196, 150],
    "black_stone": [38, 38, 42],
    "white_stone": [242, 242, 238],
    "tolerance": 48
  },
  "input": { "method": "sendinput", "offset_ms": 60 },
  "capture": { "method": "mss", "client_only": true }
}
```

- **新增一个目标程序 = 新增一个 profile**，不改一行代码。
- `tools/calibrate.py` 是标定向导：贴一张截图，用鼠标点两个角 → 自动算出 `origin` / `spacing`，并把色值采样出来，直接生成 profile。
- 识别失败时的兜底：检测不到网格就退回"模板匹配 + 比例推算"，仍失败则提示用户重新标定。

这套机制对**网页版同样成立**（浏览器窗口也是窗口）。网页额外提供更稳的 DOM 通路，作为 profile 里的 `"adapter": "web"` 分支。

## 5. 识别管线（最需要打磨的部分）

```
截图(客户区) 
  → 预处理：转灰度/HSV，去除 HUD 干扰
  → 网格检测：行/列投影取峰，得到 15 条竖线 15 条横线
      · 峰间隔近似相等 → 验证通过
      · 空盘也能检出（网格线是固定的）
  → 交点计算：line[i] ∩ line[j]
  → 每点取 5×5 中心块
      · 方差低 + 接近背景色  → 空
      · 方差低 + 暗色        → 黑
      · 方差低 + 亮色        → 白
      · 方差高                → 不确定（有棋子高光/选中框）
  → 一致性校验：15 行 × 15 列数量守恒、与上一帧 diff ≤ 2
  → 输出 BoardState + 置信度
```

**为什么不直接用 Hough**：棋盘是严格的正交网格，投影取峰比 Hough 快 10 倍且更稳，还能直接得到等距性校验。

**"残局"场景**（用户明确提到可能一次性给残局）：识别层天然支持——它只关心当前每格是什么，不关心历史。第一次读到全盘即作为初始局面。

## 6. 棋力设计（G4 的核心）

原项目的 MCTS 骨架保留，但**只把它当备选**。要"赢"，主力必须是战术搜索：

```
决策顺序（选第一个命中的）：
1. 我一步成五            → 直接下
2. 对手一步成五          → 堵（多点则认输局面，选最有价值的堵点）
3. VCF：我能连续冲四取胜 → 执行
4. 对手有 VCF 威胁       → 破坏
5. 迭代加深 αβ 搜索      → 最佳点
6. 兜底：棋型评分最高点
```

### 为什么不是纯 MCTS
五子棋是**强战术、低分支深度**的游戏，随机 rollout 几乎不可能撞到五连终局，MCTS 的胜率信号极稀疏。原项目的 `Simulate()` 用"可落子点数量之差"当分数，在五子棋里没有意义。正确做法是：

- **树搜索部分**用 αβ（深度 6~10 可达业余强手水平）
- **评估函数**用棋型打分（成五 > 活四 > 冲四/活三 > 眠三 > 活二）
- **战术层**单独处理必胜/必防，不浪费搜索深度
- MCTS 保留为第二引擎，用于"想得快但不想太深"的场景

### 性能预算
- 15×15 候选点剪枝：只取距已有棋子切比雪夫距离 ≤ 2 的空点 → 中盘约 30~60 个
- Python 单线程 αβ 深度 6 + 置换表，约 0.5~2s，够用
- 需要更快可上 `numba` 或把引擎换回 C++ 做 DLL（预留 `engine_cpp` 接口位）

## 7. 规则与执色（G5/G6）

- `engine/rules.py`：`Ruleset(config)`，`casual`（连五即胜，无禁手）/ `renju`（黑棋禁长连、双四、双三）
- 执色：不写死。运行期看第一手是谁下的——黑子先手即执黑；也支持手动指定。
- 禁手只约束黑方，且"成五"优先于禁手判定。

## 8. 目录结构

```
GomokuAI/
├── run.py                    # 唯一入口
├── config.json               # 全局配置
├── requirements.txt
├── README.md
├── engine/                   # 棋理引擎（无外部依赖）
├── vision/                   # 视觉识别
├── control/                  # 鼠标注入
├── adapters/                 # 三种对局适配器
├── app/                      # Web UI
├── profiles/                 # 各目标程序的标定文件
├── tools/                    # 标定向导 / 基准测试
├── tests/                    # 单元测试
└── docs/
```

**可移植性**：全部路径以 `Path(__file__).resolve().parent` 为基准，配置里不写绝对路径。

## 9. 实施路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| P0 | 引擎（board/patterns/tactics/search）+ 单测 | 自对弈不崩、能赢简单脚本、1 秒内出招 |
| P1 | Web UI + 本地模式 | 浏览器里能人机对弈，可选择执黑/执白 |
| P2 | 截图 + 网格标定 + 交点分类 | 对静态截图识别准确率 100% |
| P3 | 窗口适配 + 自动落子闭环 | 真实程序里能完整下完一局 |
| P4 | 增强：开局库、时间控制、异常恢复 | 残局/重开/悔棋都能正确处理 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 游戏画面 3D 透视，棋盘不是正投影 | 网格非等距 | profile 支持四点仿射标定，而非只用 origin+spacing |
| 落子有动画/高光 | 单帧误判 | 稳定帧确认：连续 2 帧一致才采纳 |
| 点击被游戏忽略 | 不下棋 | 点击后轮询验证，失败换 PostMessage 再试 |
| 反作弊 | 封号 | 本作仅本地读屏+模拟输入，不读写进程内存；但用户需自担风险 |
| 屏幕遮挡/最小化 | 截不到图 | 优先 PrintWindow 后台截图，不可用则要求窗口置前 |
